# SVID29 与异步调用链回归验证

此控制台项目使用现有项目依赖，无额外测试框架。查询测试编译生产用的 `ControlStateQuery.cs`；传输测试通过反射调用真实的托管回复、取消、超时和断线处理，并模拟本机发送返回前的回调。分发测试调用真实 KS_CM300 入口和反射分发。验证不连接设备、不加载本机 SECS DLL。

运行（依赖已还原时）：

```powershell
dotnet run --project tests/Svid29Regression/Svid29Regression.csproj --no-restore -p:OutputPath=D:/projects/EAPServer/.tmp_verify/svid29-step4/tests/
```

47 个场景覆盖：

- REMOTE/LOCAL、非法协议或数据、无回复、异常、查询期限和调用方取消。
- 待回复清理、断线结束等待、完成后的取消回调隔离。
- 本机发送返回前收到回复或超时、首个终态生效、发送中断线、发送失败和本机返回 -1。
- 并发回复按消息 ID 匹配、设备主动事件与查询 ID 冲突、提前回复缓存上限及清理、迟到回复隔离。
- 反射分发等待 Task 完成、原始异常保留、拒绝 async void 或不存在的方法。
- 实际接收入口等待回复、内层 NG 不被外层成功覆盖。
- 并发与嵌套 TraceId 隔离、带返回值的步骤以及异常传递。
- 通道重复启动、停止取消等待、旧循环退出后再重启、异常或正常退出清理、真实停止入口及快速启停无重叠。
- 24 个并发调用共享一次 SVID29 发送、设备和连接代次隔离、不缓存完成的结果、取消单个或全部等待者、失效取消及失败后重试。
- MES Batch 的 PORTID 从服务端响应对象序列化、客户端反序列化、旧响应兼容补齐，到按端口缓存查找和旧缓存修复。
- HSMS 重连后的有效通信会恢复本地 Connected 状态，旧会话迟到的 Disconnected 事件不会覆盖它。

## 已完成的三轮改动

第一轮将同步 MQ 查询和异步 REMOTE 检查统一到同一发送/解析实现，保留同步分发兼容入口。协议 T3 不变，查询等待上限为配置 T3 加 1 秒，用于本机超时回调缺失时结束等待并清理记录。连接代次用于丢弃断线前发起的查询结果。

第二轮修复快速回复早于待回复登记的竞态。仅在本机发送与登记窗口内暂存回复，最多 1024 条；窗口结束或断线后清空。设备主动消息不作为查询回复，迟到的次级回复不进入主动消息队列。不需要回复的发送使用不带 W 位的本机调用标志。

接收分发及 KS_CM300 的异步入口改为返回并等待 Task，保留接收循环的并发处理。外层仅在尚未设置结果时标记成功，补偿操作后保留原始失败。主要 CEID、MES 和协议发送等待点记录开始、结束、耗时及异常。

第三轮使用独立任务及取消源管理通道采集。停止事件等待旧循环退出，重复启动只创建一个任务，重启在旧任务清理完成后采集。断线或非 REMOTE 状态取消采集；采集等待与一秒间隔均支持取消。流量 S1F3 改为 await，采用 T3 加 1 秒的托管等待期限；定义加载加锁，采集使用快照，避免加载其他通道定义时集合被清空。后台任务使用独立 Arguments/TraceId，记录 ParentTraceId。

同一设备、同一连接/状态代次的未完成 SVID29 查询共享一个 QueryId。完成后即移除，下一次检查仍发新查询；没有状态有效期缓存。取消一个等待者不影响其他等待者，最后一个等待者取消时清理底层等待。断线及 CEID 8/9/10 控制状态事件让旧查询失效，并丢弃旧代次结果。

MES Batch 的 `PORT_ID` 原先只存在数据库模型，LOTINFODOWNLOAD 回复模型没有 `PORTID`，处理器也没有把数据库值写入回复，因此 XML 没有该节点。现在服务端把 Batch.PortId 加入响应；客户端仍为旧服务端响应提供请求端口回填，并更新已有空端口的缓存对象。缓存查询优先使用 CarrierId+PortId 精确匹配，并兼容 `2` 与 `LP2` 格式。

## 如何定位等待位置

每个 `Arguments` 有独立 TraceId，异步步骤通过 AsyncLocal 传递当前 TraceId。日志需要现有 log4net 配置正常启用。

1. 用 TraceId 找到同一次事件的 `SECS Step Begin/End`，查看尚未配对结束的内层 Step，例如 `CEID=49/SlotMapVerifyOK`、`MES_TrackIn` 或 `Send_S16F15_CreatePJ/S16F15`。
2. 遇到 REMOTE 检查，用相同 TraceId 下的 `SVID29 Wait Begin/End` 查看 Source、QueryId、Shared、结果和耗时。共享查询的多个调用方有不同 TraceId，但使用同一 QueryId；实际发送只有一组 `S1F3/SVID29 Begin/End`。
3. 用 QueryId 找到发送日志中的 MessageId，再对照 S1F4、T3 或断线日志。

步骤 End 表示等待已经结束；协议是否成功仍由业务解析及结果字段判断。仅看到 Begin 时，既可能仍在等待，也可能进程已退出，需要结合设备连接日志判断。MQ 同步兼容入口的 SVID29 查询仍可用 QueryId/Source 单独定位。

## 验证边界和后续阶段

底层仍用 null 表示发送失败、断线或本机 T3 超时，查询结果将这些保留为 NoReply，具体原因需按消息 ID 对照底层日志。查询等待上限不能中断阻塞在本机 DLL 内部的同步发送。本轮未构建或修改本机 DLL。

真机仍需验证设备无回复、断线重连、快速回复、多通道并发、停止后立即重启及 LOCAL/REMOTE 切换。查询合并减少同时等待期间的重复发送，不改变串行检查频率。其他同步发送兼容入口和 MES 等待尚未全面加入取消期限；应用整体退出时的模块生命周期管理也是后续工作。
